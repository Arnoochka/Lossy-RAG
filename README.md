# Хранение и поиск эмбеддингов в СУБД для LLM

## Общая идея

Языковая модель не знает частных и свежих данных, поэтому в RAG-системах ответ строится на фрагментах, извлечённых из базы данных. Тексты превращаются в эмбеддинги — векторы из сотен измерений, в которых смысловая близость становится геометрической. Задача СУБД — быстро находить векторы, ближайшие к вопросу. Классические индексы здесь не работают из-за проклятия размерности, а точный перебор плохо масштабируется. Поэтому появились приближённые индексы (IVF, HNSW), квантизация векторов, специализированные векторные БД и расширения обычных СУБД (pgvector). Все они платят точностью за память и скорость.

Центральная идея работы — разложить успех поиска на два множителя:

**P(правильный абзац найден) ≈ P(эмбеддинги ставят его в top-k) · P(индекс его не теряет)**

Первый множитель отвечает за качество представления смысла, это область ИИ. Второй — за качество хранения и индексации, это область СУБД. Дальше прослеживается, как потери в поиске переходят в качество ответов модели:

**Acc ≈ R · a₁ + (1 − R) · a₀**

## Теоретическая часть

### Эмбеддинги (ИИ) (Обухова Елена)

Эмбеддинг-модель — нейросеть, которая превращает текст в вектор так, что близкие по смыслу тексты оказываются рядом; близость обычно меряют косинусом. Обучаются такие модели контрастивно: приближают вопрос к правильному тексту и отталкивают от остальных. Модели различаются размером и размерностью вектора (от сотен до тысяч измерений), а также схемой работы. Bi-encoder считает векторы заранее, их и кладут в БД. Cross-encoder точнее, но годится только для переранжирования. Размерность готовых векторов можно уменьшать, например через PCA. 

### Хранение и поиск векторов (СУБД) (Колосков Виктор)

В высоких размерностях классические индексы вырождаются в перебор, поэтому используют приближённые методы двух видов. Индексы сокращают число просматриваемых векторов: IVF делит пространство на кластеры через k-means, HNSW строит граф соседей. Квантизация уменьшает размер каждого вектора: int8, бинарная, PQ. Живёт всё это в специализированных векторных БД (Qdrant, Milvus) или в виде расширений обычных СУБД (pgvector в PostgreSQL). Рядом стоит классический полнотекстовый поиск по словам (инвертированный индекс, BM25), с которым векторный часто объединяют.

### RAG и оценка (ИИ) (Глухов Кирилл)

Найденные фрагменты подставляются в промпт, и модель отвечает на их основе. Качество поиска меряют долей случаев, когда нужный фрагмент попал в top-k (recall@k, hit@k). Качество ответа меряют совпадением с эталоном: точное совпадение, F1 по словам, «содержит ответ». На ответ влияет не только то, нашёлся ли нужный фрагмент, но и сколько посторонних рядом и где он стоит в контексте.

## Эксперименты

**Данные.** Во всех блоках одна общая база кусков из всех абзацев SQuAD v1.1, её устройство описано в [dataset.md](dataset.md). Вопросы train используются в блоках 1–2, вопросы valid — в блоке 3. Всё, что подбирается (параметры индексов, параметры гибрида), подбирается на вопросах train, поэтому проверка на valid честная.

### Блок 1. Эмбеддинги (Обухова Елена)

Поиск точным перебором, метрика hit@k по эталонным кускам. Это первый множитель.

- **1.1.** Модели разного размера внутри одного семейства (small / base / large).
- **1.2.** Снижение размерности внутри одной модели: PCA и обрезание Matryoshka-эмбеддингов.

Нюансы:
- hit@k = 1, если в top-k есть хотя бы один эталонный кусок. Считается по обоим эталонам: строгий занижает (не засчитывает неразмеченные повторы ответа), мягкий завышает (может засчитать случайное совпадение слова). Истинное значение лежит между ними.
- Расширение: hit@k на перефразах для моделей разного размера. Вопрос: растёт ли устойчивость к смене слов с размером модели.

**hit@k.** Для вопроса q: G(q) — его эталонные куски из `answer_chunks` (строгий эталон — `is_annotated = True`, мягкий — все), Tₖ(q) — k кусков, которые вернул поиск.

hit@k(q) = 1, если G(q) ∩ Tₖ(q) ≠ ∅, иначе 0;  hit@k = (1/|Q|) · Σ hit@k(q).

То есть это доля вопросов, у которых хотя бы один эталонный кусок попал в выдачу. Хватает одного куска, потому что LLM достаточно одного фрагмента с ответом. При росте k метрика не убывает. От recall@k блока 2 отличается эталоном: там выдача сравнивается не с правильными кусками, а с выдачей точного перебора.

### Блок 2. Хранение и индексы (Колосков Виктор)

Метрики: recall@k относительно точного поиска, память, задержка, время построения индекса. Это второй множитель.

- **2.1. Чистый эффект квантизации.** Точный перебор по сжатым векторам: float32, float16, int8, PQ с разным m, бинарный.
- **2.2. Чистый эффект алгоритма.** Векторы без сжатия, точный перебор против IVF против HNSW.
- **2.3. Комбинации.** Проверка гипотезы независимости ошибок: r ≈ r₁ · r₂.
- **2.4. Способ поиска.** Векторы против BM25 против гибрида.

Нюансы 2.1–2.3:
- Эталон E(q) — k ближайших кусков, найденных точным перебором по полным float32-векторам. Он считается один раз. Для ответа индекса A(q): recall@k = |A(q) ∩ E(q)| / k, затем среднее по запросам.
- 2.1: recall не может быть больше 1, сжатие только сохраняет совпадение с эталоном или ухудшает его.
- 2.3: r₁ берётся из 2.1, r₂ — из 2.2. Если r заметно выше r₁ · r₂, ошибки связаны: оба метода спотыкаются на одних и тех же запросах. Если заметно ниже, методы мешают друг другу: например, квантизация искажает расстояния и сбивает навигацию по графу HNSW.

Нюансы 2.4:
- Эталон — эталонные куски, метрика hit@k, как в блоке 1.
- Гибрид: каждый поиск выдаёт 50–100 кандидатов, списки сливаются, из объединения берётся top-k. Шкалы косинуса и BM25 разные, поэтому есть два способа слияния:
  - **RRF:** RRF(d) = Σ 1 / (c + rank(d)), сумма по спискам, c = 60 (значение из статьи Cormack et al., 2009). Константа названа c, чтобы не путать её с k из top-k;
  - **взвешенная сумма:** α · s_vec + (1 − α) · s_BM25, где оценки каждой выдачи приведены к [0, 1] min-max нормировкой (s − min) / (max − min). Кривая hit@k(α): α = 0 — чистый BM25, α = 1 — чистые векторы.
- Вопросы стоит разбить на четыре группы: нашли оба метода, только векторы, только BM25, никто. Если обе группы «только …» заметные, гибрид находит больше любого метода по отдельности.
- SQuAD удобен для BM25: вопросы писали, глядя на абзац, поэтому слова сильно совпадают. Победа BM25 здесь ожидаема и объясняет, зачем на практике нужен гибрид.
- Перефразы сравниваются с исходными вопросами на том же подмножестве, попарно. Гипотеза: hit@k у BM25 падает сильнее, чем у векторов. Можно построить hit@k в зависимости от доли совпадающих слов вопроса и абзаца.

### Блок 3. Ответы LLM (Глухов Кирилл)

Проводится на вопросах valid, на нескольких характерных конфигурациях из блоков 1–2.

- **3.0. Пилот.** Без контекста и с правильным абзацем, это даёт a₀ и a₁.
- **3.1.** Проверка модели Acc ≈ R · a₁ + (1 − R) · a₀.
- **3.2.** Оптимальное число фрагментов в контексте.
- **3.3.** Позиция правильного фрагмента в контексте.

Нюансы:
- Пилот заодно проверяет перефразы: если a₁ на них почти не падает, их можно брать в блок 3; если падает сильно, блок 3 идёт только на исходных вопросах.
- R и деление вопросов на «нашёлся / не нашёлся» зависят от эталона (строгий или мягкий). Если модель стабильно отвечает правильно на кусках, которые засчитал только мягкий эталон, неразмеченные повторы ответа действительно полезны.
- Если в промпте будут few-shot примеры, они берутся из вопросов train.

**Оценка ответа.** Ответ проверяет LLM-судья — большая внешняя модель. Ей по одной строке дают вопрос, эталонные ответы и ответ модели, без контекста, и просят вердикт одним словом: CORRECT или INCORRECT. В промпте прямо сказано сравнивать только с эталоном, а не со своими знаниями.

**Acc ≈ R · a₁ + (1 − R) · a₀.** Это формула полной вероятности для событий F = «эталонный кусок попал в контекст» и C = «LLM ответила правильно»:

P(C) = P(C | F) · P(F) + P(C | ¬F) · P(¬F).

- **R = P(F)** — hit@k конфигурации при том же k, сколько кусков идёт в промпт. Эмбеддинги и индекс влияют на ответ только через R.
- **a₁ = P(C | F)** — точность, когда нужный фрагмент есть (пилот 3.0: модели дают правильный абзац).
- **a₀ = P(C | ¬F)** — точность без нужного фрагмента, то есть насколько модель знает или угадывает сама (пилот 3.0: без контекста).

Знак «≈» стоит потому, что a₁ и a₀ берутся из пилота, одни на все конфигурации. Пункт 3.1 проверяет именно это. Если реальная точность ниже предсказанной, значит, посторонние куски рядом с правильным мешают модели; этим занимаются пункты 3.2 и 3.3.

Формула линейна по R: ΔAcc ≈ (a₁ − a₀) · ΔR. Улучшение поиска переходит в точность ответов с коэффициентом a₁ − a₀. Например, при a₁ = 0.8, a₀ = 0.2 падение R с 0.90 до 0.85 снижает точность примерно на 0.03. Если a₁ ≈ a₀, качество индекса на ответы почти не влияет.
